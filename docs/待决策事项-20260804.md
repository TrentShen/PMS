## 一、权限与产品语义(影响用户体验,建议优先决策)

### 1.1 dept_leader 看隔级下属的互评汇总,目前 403

- **现状**:`peer.py:519` 互评汇总只允许直属上级/HR;但校准视图(`calibration.py:437`)里 dept_leader 能看到同一个人的校准分数。两端可见性不一致。
- **影响**:dept_leader 校准时只能看到分数,看不到互评内容作为依据,决策信息不全。
- **选项 A(维持现状)**:守住"互评内容仅直属上级可见"的保密原则。
- **选项 B(放宽)**:dept_leader 可看自己部门内所有人的互评汇总,校准体验一致。
- **建议**:B。校准本身就要定这个部门的分,看不到依据不合理;互评汇总对 dept_leader 开放风险可控。

### 1.2 Leader 未被 HR 加进周期时,完全无入口

- **现状**:`cycles.py:109-131` 非 HR 只能看到"自己作为参与人"的周期;HR 漏加 Leader,Leader 就看不到任何周期。
- **影响**:依赖 HR 操作不遗漏;漏加后 Leader 无感知、无法自评/评价下属。
- **选项 A(维持)**:流程可控,责任在 HR。
- **选项 B**:有下属在周期中即可见该周期(自动获得入口)。
- **建议**:B。100 人团队 HR 就一两个人,漏加是大概率事件;可见性扩大到"有下属在周期"风险很小。

### 1.3 校准提交要求全周期(含外部门)全员有分

- **现状**:`calibration.py:379-385` 提交时校验**全周期**所有参与人都有最终分,任一为空即 400。dept_leader 有提交权限,但会被外部门未评分卡住。
- **影响**:dept_leader 的提交权限实际不可用,只能等 HR 统一提交。
- **选项 A(维持)**:HR 统一提交,dept_leader 按钮可以后续隐藏。
- **选项 B**:按部门/scope 校验,允许部门先提交。
- **建议**:A(维持)+ 前端把 dept_leader 的提交按钮隐藏或置灰并提示"由 HR 统一提交"。部门自提交涉及审批流语义变化,灰度期不值得动。

### 1.4 is_hr_dept_leader 两处判定口径不一致

- **现状**:`auth.py:92-109` 按 base_role 判定,`scope.py:96-107` 按当前生效角色判定。超管切换视角测试时,可能出现一处判真一处判假。
- **影响**:**仅影响超管切视角的测试场景,真实用户无影响**(审计报告原话)。
- **选项**:统一为"生效角色"(推荐,测试视角与数据范围一致)或统一为 base_role。
- **建议**:统一为生效角色,改动小。低优先。

### 1.5 LeaderEvalDetail 需要"退回"功能吗

- **现状**:Leader 评价提交后没有退回/撤回入口;后端无退回接口,前端当时未新造。
- **影响**:Leader 填错只能找 HR 处理。
- **选项 A(不做)**:维持"提交即定稿",找 HR 兜底。
- **选项 B(做)**:加退回接口 + 前端按钮,涉及状态机变更(已提交 → 草稿)。
- **建议**:灰度期先 A,收集实际使用中填错的频率再定。

### 1.6 自评时删除互评人,需要二次确认吗

- **现状**:自评页面删除互评人走 antd Select 内建的关闭按钮,无二次确认,点了就删。
- **影响**:误触直接删除,需重新添加。
- **选项 A(维持)/ B(加 Popconfirm 二次确认)**。
- **建议**:B,改动 5 行以内,确认后我直接修。

## 三、安全机制(灰度期可接受,正式推广前建议闭环)

### 3.1 JWT 7 天有效期,无刷新、无吊销

- **现状**:token 签发后 7 天内有效,员工离职/角色变更无法立即吊销。
- **影响**:离职员工 token 在 7 天内仍可用(需企微侧停应用兜底)。
- **选项 A(维持)/ B(加 Redis 吊销列表,改动中等)/ C(缩短有效期到 1 天 + 企微静默续登)**。
- **建议**:C 最省事——企微 H5 本来就走静默授权,缩短有效期用户无感。

### 3.2 OAuth state 不校验

- **现状**:企微 OAuth 回调未校验 state 参数,理论上有 CSRF 风险。
- **影响**:攻击者可以诱导用户用攻击者的 code 完成回调绑定,实际利用难度较高。
- **建议**:做,改动集中在 `auth.py` + `AuthCallback.tsx`,但需要完整回归登录流程,建议单独安排一次验证后再上。

### 3.3 `fix_participants.sql` 手工改数路径

- **现状**:仓库根目录有一个手工 INSERT 参与人的 SQL,说明存在绕过应用层直接改库的运维路径。
- **影响**:绕过审计日志和权限校验,数据一致性全靠手工保证。
- **建议**:确认该 SQL 解决的问题现在是否有正规入口(参与人管理);有就删掉这个文件。

### 3.4 `_assign_leader_roles` 只升不降

- **现状**:通讯录同步时,用户被任命为 Leader 会自动升角色,但不再担任 Leader 时角色不会降回。
- **影响**:卸任 Leader 保留 Leader 权限,需人工改。
- **选项 A(维持,人工兜底)/ B(同步时双向调整,需注意 HR 手动设置的角色可能被误降)**。
- **建议**:A + 在 HR 控制台用户列表把"角色与职务不符"的标出来即可,自动降级误伤风险大。

### 3.5 邮件降级重试是死代码

- **现状**:企微发送失败降级邮件的重试函数没有调度入口,从未执行过。
- **选项 A(挂到调度器,10 行)/ B(删除死代码)**。
- **建议**:先确认你要不要邮件通道这个能力——目前邮件通道本身是否配置过?没配置过就选 B 删掉。

### 3.6 权限缓存失效最长延迟 10 分钟

- **现状**:scope/user 缓存的失效函数全项目零调用;改角色/部门后,最长 10 分钟旧权限仍生效。
